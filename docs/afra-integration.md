## Choices, and where each comes from

| choice | value | evidence |
| --- | --- | --- |
| Java release | **17** | `<compilerversion>17</compilerversion>` in the `properties` block of both `org.rebecalang.compiler/pom.xml` and `org.rebecalang.modelchecker/pom.xml`, applied via `maven-compiler-plugin`'s `<release>` |
| build tool | **Maven** | every Rebeca repository is a Maven project |
| compiler plugin | **3.11.0** | `org.apache.maven.plugins.compiler.version` in the same poms |
| surefire | **3.2.2** | `org.apache.maven.plugins.surefire.version`, ditto |
| JUnit | **Jupiter 5.10.1** | `junit.jupiter.version`, ditto |
| packaging | plain jar with a `Main-Class` | see below |
| runtime dependencies | **none** | see below |

Pinning the Java release matters: a class file compiled for a newer release
cannot be loaded by Afra's JVM, and Afra targets 17.

The versions the official build uses that this project does **not** adopt are
Spring (6.1.20), Lombok (1.18.30) and log4j (2.25.4). They are infrastructure
for the compiler and model checker; a reducer that reads one file and writes
five needs none of them, and taking them on would create exactly the version
conflicts this project is trying to avoid.

## Packaging

The official compiler builds a `jar-with-dependencies` via
`maven-assembly-plugin`. This project has no dependencies, so a plain jar with a
`Main-Class` manifest is enough — `mvn package` produces `target/awtr.jar`,
runnable directly and droppable onto a classpath as a library.

That is deliberate. Afra is an Eclipse RCP application with its own XML stack and
its own Spring context. A dependency-free jar cannot collide with either. Had
this project taken a JSON binding library, embedding it would mean either
shading it or negotiating a version with Afra's own transitive graph.
`BoundaryTest.noThirdPartyRuntimeDependencies` fails the build if a
non-JDK import appears.

## How an in-process Afra adapter would plug in

The whole boundary is one method:

```java
@FunctionalInterface
public interface TransitionSystemSource {
    RawTransitionSystem load();
}
```

An adapter that reads Afra's in-memory model rather than a file has to:

1. implement `TransitionSystemSource`;
2. build a `RawTransitionSystem` with `RawTransitionSystem.builder(id)`, adding
   each state with `state(id, atomicPropositions)` — **the initial state first**,
   or else call `initialState(id)` explicitly;
3. add each transition as `RawTransition.message(source, target, new ActionIdentity(sender, owner, title), executionTime, shift)`
   or `RawTransition.time(source, target, units, executionTime, shift)`;
4. call `ReductionService.reduce(source, request)`.

Nothing else changes. Hiding, refinement, quotient construction, verification
and serialisation are all written against `RawTransitionSystem` and never learn
where the model came from. `AdapterContractTest.aHandBuiltSourceIsEnough`
demonstrates exactly this in four lines.

The classes a plug-in would need on its classpath are `TransitionSystemSource`,
`RawTransitionSystem`, `RawTransition`, `ActionIdentity`, `ObservableSet`,
`ReductionRequest`, `ReductionService`, and — if it wants to write files —
`ArtifactWriter`.

### Where the model would come from inside Afra

`org.rebecalang.modelchecker` holds the Timed Rebeca model checker in Java
(`TimedRebecaModelChecker`, `TimedState`, `TimedActorState`). Note that its
`TransitionSystem` enum currently offers only `TRANSITION_SYSTEM_FTTS` and
`TRANSITION_SYSTEM_FGTS`; the plain TTS search that emits `<time>` steps lives in
the **C++** side generated by `org.rebecalang.rmc`
(`TTSPatchTemplate.vm`). An in-process adapter therefore has a choice to make
that is outside this phase's scope:

* drive the RMC-generated model checker and read its `.statespace` — which is
  what the file adapter already does, so the "in-process" gain would be only
  process management; or
* add a TTS mode to the Java model checker and adapt its states directly, which
  is a change to Afra rather than to this tool.

That decision needs the supervisor. It does not affect this tool's design either
way, because both end at the same one-method boundary.

## Not done in this phase

The Afra plug-in itself. `Instruction.md` scopes it out, and nothing here
depends on it: the standalone application is the deliverable, and the seam above
is the preparation for it.
